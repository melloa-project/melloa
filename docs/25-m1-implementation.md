# M1 implementation: trustworthy conversation and owner inspection

## Purpose

Track the second implementation milestone in [the final synthesis](22-final-synthesis.md#first-implementation-milestones) against reviewed code, tests, and remaining acceptance gates. This page reports implementation status; it does not supersede the architecture, [adopted decisions](23-v0.2-decisions.md), or accepted ADRs.

**Status:** In progress with one usable owner slice that remains process-local by default and can explicitly enable partial PostgreSQL restart durability. Authentication, canonical conversation, a deletion-ready assertion-content boundary, process-local owner-triggered assertion-content deletion, cited retrieval, correction, structured inspection, authenticated health/media/cost/disclosure and retention-policy views, provider-failure retry/resume, exact outbound authorization, durable outbound delivery recovery, authenticated delivery APIs, bounded synthetic delivery execution, a real local/private OpenAI-compatible model route, an explicitly bounded experimental subscription-backed Codex CLI route, a conversation-first React Owner Console, reproducible visual smoke evidence, optional durable runtime wiring, a real optional Telegram Bot API path with private pairing, canonical text ingestion, model routing, and policy-authorized replies, and a validated canonical JSONL/schema/checksum export preview are implemented. PostgreSQL mode also preserves Telegram pairing and revocation authority, normalized intake receipts, poll offsets, and accepted-but-not-submitted reply recovery across an ordinary core restart. M1 is not complete until remaining process-local sessions and observations, event/audit emission, durable retention/deletion operations, attachment storage, encrypted export packaging, logical snapshots/blob export, backup/recovery, broader workers, and the remaining acceptance gates are delivered.

## Retrieval and disclosure invariants

- Every completed conversation turn references a retrieval manifest, including turns with no relevant citations.
- The manifest records a hash of the query rather than duplicating raw owner text.
- Relational/full-text matching generates candidates; similarity alone is never represented as evidence.
- Disputed, retracted, superseded, unrelated, and out-of-scope sensitivity records are excluded before model context assembly.
- Ranking is deterministic and combines query overlap, confidence, source authority, confirmation status, and a stable recency/ID tie-break.
- A model may cite only citation IDs present in that turn's manifest. The output message retains citation IDs and the turn retains their assertion/evidence IDs.
- Route and derived-message sensitivity are at least as restrictive as every cited memory object.
- The persisted manifest records actual model-result disclosure, including disclosure by a failed hosted fallback attempt.
- External disclosure accounting records every retrieval citation sent in model context even when the generated answer cites only a subset. Output citations remain separately identifiable.
- Device-only cited memory cannot be marked externally disclosed; validation fails before a reply or turn is persisted.
- Guardian `offline` and `no-actions` permit only device model routes. Private-network and approved-provider routes, including Codex CLI, become eligible only in `normal`; an ineligible route receives no prompt and records no disclosure attempt.
- Turn, output message, model result, and retrieval manifest are checked and written as one logical completion boundary by the conversation store port.

## Current runtime persistence boundary

The retrieval implementation has both an immutable in-memory repository and a PostgreSQL read adapter over assertions, provenance, and the mutable correction projection. Integration fixtures remain synthetic and contain no embeddings, provider credentials, personal records, or external calls. Full-text token overlap is only a deterministic candidate baseline; a future `pgvector` index remains rebuildable and non-authoritative.

The default test model and outbound client adapters remain deterministic fakes. The explicit MVP additionally supports reviewed OpenAI-compatible HTTP routes to loopback or private endpoints, including local Ollama, LM Studio, vLLM, and llama.cpp-style servers. It can also register an experimental subscription-backed Codex CLI as an approved-provider route only from explicit owner configuration. That process receives a bounded prompt on standard input, its isolated subscription authentication, and fixed read-only/no-approval/ephemeral flags; it receives no Guardian, deterministic-policy, Melloa credential-broker, or capability authority. The CLI sandbox is not treated as production host isolation, and unavailable token/subscription-cost metadata is labelled rather than presented as measured zero. Approved-provider routes require explicit disclosure and retention configuration; no direct paid API or CLI route is configured by default. Outbound delivery has both process-local and PostgreSQL leased stores, with exact policy, attempt, adapter, and execution records persisted transactionally. The fake model route remains clearly labelled and performs no network call.

The explicit runtimes keep the real signed Guardian read boundary. `serve-synthetic` and default `serve-mvp` compose in-memory stores, seed one synthetic assertion for retrieval/correction drills, and print its non-secret ID. Supplying a private core-role DSN file to `serve-mvp` instead wires PostgreSQL conversation, memory, delivery, and Telegram adapters after an advisory-lock-protected, exact canonical owner/Melli/seed bootstrap. Canonical threads/messages/turns, retrieval manifests, model runs/disclosures, correction state/history, reply/delivery work, Telegram pairing candidates/confirmations/revocations, normalized updates/receipts, and the monotonic poll cursor then survive a core restart. Durable intake receipts let a new reply dispatcher reconstruct accepted messages whose completed replies have not yet been submitted to delivery. Store calls are serialized over four dedicated connections so request, reply, delivery, and Telegram worker threads cannot share one transaction boundary. Startup and authenticated health report that scope explicitly and fail closed on an unavailable database, missing or incompatible schema, public/opaque target, unsafe DSN file, or immutable bootstrap conflict; there is no silent memory fallback.

Workers remain process-local executors even when their PostgreSQL queues and Telegram state are durable. Owner sessions, provider health observations, Telegram challenge-send outcome/deduplication, attachment quarantine bytes, event/audit emission, retention inventory, and backup remain ephemeral, synthetic, unassembled, or disabled. The export preview covers canonical conversation and memory-inspection records only; it is validation-ready JSONL rather than encrypted backup, blob export, signed archive, logical database snapshot, or database import execution. Ambiguous external-send outcomes also remain deliberately unretried rather than being guessed successful. The authenticated health and retention reports label those disabled/partial coverage facts rather than presenting restart durability, retraction, or process restart as deletion. The Owner Console exposes assertion content deletion only through the exact recent-authenticated memory mutation path; the process-local store removes the retained value while preserving metadata, state history, tombstone evidence, rebuild-work obligation, and a reported backup-expiry state such as `not_configured` rather than claiming backup erasure. PostgreSQL assertion-content deletion remains deliberately uninstalled and fails closed instead of claiming durable erasure. React escapes API- and owner-controlled text. The ordinary `serve` command remains the unconfigured status-only surface rather than silently selecting application services.

Telegram remains an optional secondary adapter. The no-network default is synthetic, while an exact mode-`0600` token file enables bounded Bot API long polling, challenge delivery, and policy-authorized text replies behind the same pairing, canonical conversation, model-routing, and delivery boundaries. An unpaired private `/start` creates an immutable expiring candidate. For the Bot API route, its high-entropy code is derived with a domain-separated HMAC from the configured bot credential and candidate ID, so it is stable across a restart without storing plaintext; durable candidate state retains only the hash. Challenge-send outcome and deduplication remain process-local and are disclosed as such. The private API lists only redacted candidate metadata, requires the exact authenticated owner for reads, and requires CSRF plus recent authentication to confirm or revoke. The Owner Console projects this optional binding, masks provider identifiers, accepts the challenge through a transient DOM field, clears that field before mutation, never copies the code into long-lived console state or persistent storage, and requires live recent authentication plus an explicit confirmation before confirm or revoke. Activation is denied in `offline`, `read-only`, `stopped`, and `recovery`, while revocation remains authority-reducing and available. The normalized source never consumes updates on poll and can replay after transient outage; complete observations/outcomes precede offset advancement, and changed content, challenge derivation, receipts, stale writers, and offset regression fail closed. Ingestion calls the credential-free immutable attachment-intake port only after exact pairing validation, rejects a backend bound to another owner, validates its complete ordered outcome before canonical mutation, and creates canonical attachment parts only from quarantined Melloa-owned references. The explicit runtime selects the no-network metadata-rejecting backend; known attachment and unsupported-content metadata is rejected before any Bot API file fetch. The bounded in-memory quarantine remains a synthetic test foundation, exposes no content read, enforces a one-hour-to-seven-day expiry policy, preserves deduplicated content until its newest exact reference expires, and emits content-free deletion tombstones while reclaiming its hard quota. Automatic expiry is permitted only in Guardian `normal` and `offline`; `no-actions`, `read-only`, `stopped`, and `recovery` suspend it before backend access. The worker rejects over-limit, duplicate, or foreign-owner receipts and exposes only counts, timestamps, bounds, and redacted reason codes in health. No production attachment fetch/blob backend exists.

M1 media inspection is metadata-only. The synthetic catalog truthfully reports capture disabled and zero retained items. The versioned contract can represent event boundaries, interpretation confidence, missing intervals, sensitivity, retention/expiry state, content hashes, and disclosure record IDs, but its content endpoint is fixed to unavailable. It exposes no blob URL, filesystem path, camera address, or credential. Actual camera installation/capture remains M3, and deletion controls remain part of the retention gate.

The model-activity report is deliberately redacted: it exposes route, provider, model, token, cost, timing, purpose, external-attempt, triggering-message, and disclosed-memory identifiers without duplicating prompts or raw model output. Its default window is seven days, explicit windows are half-open and capped at 366 days, and PostgreSQL selection is scoped through the authenticated owner's canonical conversation threads.

The browser client never reads or persists the HTTP-only session cookie, CSRF proof, owner credential, or pending message idempotency key. Login returns a CSRF proof held only in the page's memory; a restored cookie session remains read-capable but must reauthenticate before browser mutations. React renders API- and owner-controlled values as text rather than interpreted markup. The loopback production server forwards only `/api/` and `/health/` to the configured private core so browser requests remain same-origin.

Browser submission retries retain one in-memory idempotency key only until the canonical inbound message is durably accepted. The core then owns reply execution independently of the request: a failed provider or invalid result returns authenticated `202 Accepted` with a redacted error code and retry time, due work resumes under a lease, exhausted work becomes visible `dead` state, and a CSRF-bound owner action appends resumption metadata before granting another bounded attempt budget. Every retry preserves the immutable inbound message and creates at most one completed turn; known failed model attempts retain disclosure and sent-memory identifiers without exposing raw exception text. Memory mutation controls disable themselves when recent authentication expires, require explicit confirmation for immutable state changes, and send the visible optimistic projection version. An aggregate timeline and richer storage/backup telemetry remain deferred rather than presenting synthetic records as real observations.

Outbound adapters no longer accept a string that merely looks like a policy decision ID. The authorized-delivery contract carries the canonical message, request, and full decision; validates the request/decision/action-hash chain, `allow` effect, chronology, expiry, destination, message hash, sensitivity, R2 classification, and external-communication effect; and then rechecks adapter identity and live expiry at execution. The synthetic adapter uses one stable idempotency key across attempts, returns an exact replay for a repeated attempt, and reuses the original external receipt without sending the canonical message twice. The private API lists and inspects complete redacted status, requires recent authentication plus CSRF for enqueue/resume, returns `202 Accepted` whenever work is not completed, conceals foreign or cross-thread work, and never exposes raw adapter/policy failure details. The explicit synthetic runtime executes this path through a bounded background worker and fake in-memory route. The Owner Console obtains the canonical status rather than creating a competing summary record, projects queued/running/dead/completed state plus attempt/resumption history, retains a pending idempotency key only until acceptance, and requires recent authentication plus explicit confirmation for initial or resumed delivery.

## Telegram canonical-ingestion invariants

- Telegram ingestion requires one pre-existing canonical thread owned by the configured local owner and one exact confirmed owner/user/private-chat pairing. It neither creates identity/history authority nor fabricates an Owner Console session.
- Canonical acceptance is keyed by the adapter identity plus Telegram `update_id`. The message is owner-authored in canonical history, identifies Telegram only as `source_client`, inherits thread sensitivity, uses provider send time as `observed_at`, and uses normalized receipt time as `created_at`.
- Every accepted update atomically creates at most one canonical message and one reply-work item. Pairing mismatch, revocation, and user/chat mismatch create typed metadata-only rejections; attachment-only input is accepted only when at least one exact reference has a validated quarantine receipt, while an all-rejected attachment-only update advances through a typed rejection without canonical content.
- Guardian, owner-thread, poll-revision, and exact pairing checks all precede attachment-backend access. Unauthorized references receive metadata-only `source_not_authorized` outcomes without a fetch, and a transient or malformed backend outcome leaves both canonical conversation and cursor state unchanged.
- Canonical attachment parts contain only the quarantine blob ID, normalized media type, and content hash returned for the exact ordered request. Conversation processing sends owner text when present or a fixed attachment-count summary otherwise; it never places attachment bytes, hashes, blob IDs, names, or media types in the model request.
- The safe crash order is attachment quarantine, canonical `append_inbound`, then Telegram observation/receipt commit and cursor advancement. A crash between the canonical and cursor writes reuses the backend's exact cached receipt without fetching again, resolves the existing canonical idempotency binding, creates no second work item, and only then advances the cursor.
- `offline`, `read-only`, `stopped`, and `recovery` deny new Telegram ingestion before either store mutates. `normal` and `no-actions` permit already-paired conversation intake; exact immutable receipt replay remains read-only. Pairing challenge publication, pairing confirmation, and outbound replies require `normal`, so `no-actions` never emits an external challenge or activates channel authority.
- Each worker cycle constructs one positive, capped long-poll request from the durable offset and validates the complete source batch for limit, unique ascending IDs, and offset compliance before accepting any item. A source outage therefore leaves both canonical conversation and cursor state unchanged.
- In Guardian `normal`, an unpaired exact private `/start` creates one immutable candidate and idempotently publishes a replay-stable code back through the same bot; only its hash is retained in pairing state or exposed through contracts. The private API omits that hash and all plaintext challenge material.
- Confirmation requires the exact local owner, CSRF, a live recent-authentication window, the candidate-bound code, an unexpired candidate, and Guardian `normal`. A consumed candidate cannot reactivate a revoked pair, and Telegram input never fabricates an authenticated owner principal.
- `serve-synthetic` and unconfigured `serve-mvp` retain a clearly labelled no-network Telegram fixture. Supplying an exact mode-`0600` token file to `serve-mvp` replaces only the source, challenge publisher, code issuer, and delivery adapter with Bot API implementations; canonical conversation, pairing, policy, provenance, and Guardian authority remain unchanged.
- The Bot API transport accepts only the canonical public HTTPS origin or an explicit localhost/private-literal endpoint, never places the token in a query parameter, bounds timeouts and response bytes, validates every normalized update before canonical acceptance, and maps failures to redacted reason codes. Known attachment and unsupported-content metadata is rejected before file fetch.
- Telegram replies resolve the immutable `telegram:pairing:<pairing_id>` resource, require the active exact pairing, and are authorized only as Melli's direct reply to the triggering owner message from that adapter. Successful sends deduplicate within the process; a send with an ambiguous outcome fails permanently rather than risking an automatic duplicate.
- The Owner Console treats pairing as an optional Settings binding rather than conversation authority. It displays only redacted provider identifiers and lifecycle metadata, clears the challenge input before mutation, holds no challenge in application state or browser storage, requires recent authentication and explicit confirmation, refreshes both candidate and active-pair projections after changes, and renders an unconfigured adapter without degrading canonical conversation.
- Attachment intake requests bind adapter ID, update ID, full normalized-update fingerprint, receipt time, and the exact ordered references. Ingestion validates one post-receipt outcome for every reference in the same order before writing canonical state. The rejecting fake returns complete metadata-only outcomes without a fetch; the synthetic quarantine applies explicit kind/type/per-object/total-byte limits before access, hashes and content-addresses permitted bytes, exposes no content read, and returns exact cached outcomes on replay. Its retention sweep deletes only due blobs in deterministic bounded order, preserves an immutable hash/size/policy/chronology tombstone, and fails atomically if receipt identity conflicts. A separately bounded automatic worker allows this local deletion in `normal` and `offline`, denies it before backend access in all mutation/side-effect-forbidden modes, validates owner scope and receipt uniqueness, and reports only redacted aggregate health.

## Correction and contestation invariants

- Memory inspection returns the immutable assertion, its current-state projection, touching provenance edges, and complete append-only state history.
- Correction accepts only an authenticated owner session with valid CSRF proof and a live recent-authentication window.
- The target subject, predicate, temporal scope, and sensitivity are preserved; the replacement is owner-authored, confirmed, and linked with `CORRECTS` provenance.
- The original assertion document remains unchanged while its projection atomically becomes `superseded` and points to the preferred correction.
- Dispute and retraction append explicit owner-attributed state changes. They never relabel the immutable assertion document or silently erase earlier states.
- Content deletion requires the same authenticated owner, CSRF, recent-authentication, and Guardian write gates. It removes only the retained assertion value, keeps metadata/provenance/state history inspectable, records a content-free tombstone plus rebuild work, and discloses the current backup-expiry state rather than claiming complete erasure.
- Callers provide the expected projection version. Stale versions or immutable identifier collisions roll back the assertion, provenance, projection, and history write together.
- `read-only`, `stopped`, and `recovery` Guardian modes deny correction writes without granting the core role direct projection mutation privileges.

## Remaining M1 gates

- Durable owner deletion/retention-change controls beyond process-local memory content deletion and quarantine expiry, workers beyond quarantine, inventory coverage backed by canonical stores, encrypted export packaging, blob and logical SQL export, signed archives, real import/migration execution, threat review completion, observability, production operational runbooks, and full clean acceptance evidence.

No remaining item may weaken Guardian independence, deterministic policy authority, private networking, application authentication, provenance, or channel neutrality.
