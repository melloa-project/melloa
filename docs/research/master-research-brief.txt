# Master Research Prompt: Design a Long-Lived Personal AI Operating System

# Naming and Agent Identity

Use the following working terminology throughout the design:

* **Melloa** — the overall open-source system, infrastructure, runtime, protocols, memory architecture, capability framework, and deployment environment.
* **Melli** — the primary persistent personal intelligence instantiated within a Melloa deployment.

These concepts must remain architecturally distinct.

A Melloa installation may eventually host **multiple persistent intelligences or agents**, potentially with different identities, responsibilities, memories, permissions, personalities, and levels of autonomy.

For example:

```text
Melloa
├── Melli      Primary personal intelligence
├── Nova       Possible specialist/research intelligence
└── Charlie    Possible specialist/operational intelligence
```

These names are illustrative rather than predefined roles.

Do not prematurely assume a rigid multi-agent architecture merely because multiple identities may exist. Research whether separate persistent agents are actually useful compared with one intelligence using temporary specialist workers.

However, ensure that the architecture does not unnecessarily equate:

```text
system == agent == model == process
```

These should be separate concepts.

In particular, investigate the distinction between:

* the Melloa runtime,
* a persistent intelligence,
* its identity,
* its long-term memory,
* its goals and relationships,
* temporary agent processes,
* specialist agents,
* underlying foundation models,
* model providers,
* tools/capabilities.

A persistent intelligence such as Melli should not cease conceptually to exist simply because its underlying model changes from one provider or model version to another.

Treat identity continuity as an architectural question worth exploring.

Long term, it may also be desirable for a persistent intelligence to choose or change its own name rather than having identity permanently dictated by the software.

For now, use **Melloa** and **Melli** as working names throughout the specifications, diagrams, repository examples, and documentation.

Before recommending them as final public names, perform appropriate checks for:

* existing software/projects,
* GitHub namespace collisions,
* package registries,
* domains,
* search-engine distinctiveness,
* existing AI products,
* trademarks and likely brand confusion.

Do not allow naming research to block architectural work.


## Your role

Act as a combination of:

* principal distributed-systems architect,
* AI/agent-systems researcher,
* security engineer,
* privacy engineer,
* SRE / infrastructure engineer,
* open-source maintainer,
* developer-experience engineer,
* hardware/IoT architect,
* product systems thinker,
* adversarial design reviewer.

You are designing the foundations of a system intended to evolve continuously for **many years, potentially 6–10+ years**.

Do **not** treat this as a conventional productivity application.

The central thesis is:

> The enduring product is the closed-loop relationship between a human, their goals, observations about their real life, an AI reasoning system, and software/hardware capabilities that the AI can continuously create and modify.

Individual applications, dashboards, automations, interfaces, databases, websites, mobile apps, and other tools should be considered potentially **ephemeral manifestations of that loop**.

The system should be capable of observing, reasoning, acting, learning from outcomes, proposing changes, building tools, deploying them, measuring whether they helped, and iterating.

Your immediate task is **research and architecture**, not implementation.

Do not write production code unless tiny snippets are required to clarify an architectural idea.

# 1. Ultimate vision

The primary objective is personal.

Imagine this system operating successfully seven years from now.

Its owner should feel substantially “supercharged” by it.

It should resemble an extraordinarily capable long-term personal assistant or “Jarvis-like” system that:

* understands the owner's long-term objectives,
* develops a progressively deeper model of their behaviour and environment,
* processes vastly more information than a human assistant could,
* notices patterns the owner would otherwise miss,
* communicates proactively when useful,
* helps make decisions,
* creates software or workflows when they would help,
* modifies those systems over time,
* evaluates whether its interventions actually worked,
* and collaborates with the person toward objectives they deliberately choose.

The human ultimately controls the objectives.

Once an objective and its governing policies are defined, however, the AI should be capable of substantial autonomous action rather than requiring approval for every small step.

The long-term aspiration is not merely “an assistant with integrations.”

It is:

> A persistent, continuously improving human–AI system whose capabilities can expand over years.

---

# 2. Secondary vision: reproducible open-source system

Although initially built for one technically sophisticated user, **open-source quality is a first-class requirement from day one**.

This is not primarily because mass adoption is immediately required.

Rather:

* clean open-source architecture improves maintainability,
* explicit interfaces reduce coupling,
* documentation forces clarity,
* reproducible deployments reduce personal operational burden,
* public-quality engineering discourages hidden assumptions,
* modularity makes experimentation safer,
* future contributors should be able to understand the system.

The eventual target user is:

> An engineer comfortable with terminals, Docker, Git, configuration files, API keys, cloud services, and basic systems administration.

Do **not** optimize the initial system for non-technical users.

Do **not** compromise the architecture in an attempt to make onboarding completely frictionless.

It is acceptable—and desirable—to provide a strongly opinionated, blessed deployment path.

One excellent supported setup is preferable to twelve mediocre configurations.

Extensibility should come from clean abstractions, not from making every design decision configurable.

# 6. Initial MVP

The first useful deployment is intentionally narrow.

Assume the first user is the system's creator.

The initial two high-level interfaces are likely:

### A. Camera observation

An always-available camera observing a private room.

The intent is not to stream continuous video to expensive multimodal models.

Investigate a hierarchical perception pipeline such as:

1. local camera capture,
2. cheap motion / scene-change / object-change detection,
3. event segmentation,
4. selective frame capture,
5. cheap local interpretation where possible,
6. escalation to stronger multimodal models only when justified,
7. structured event creation,
8. storage according to retention/privacy policy.

Example events might include:

* person entered room,
* person left room,
* lights changed,
* person went to bed,
* person began exercising,
* desk became occupied,
* unusual activity occurred.

Treat these as probabilistic interpretations, **not ground truth**.

The system must model uncertainty.

When uncertainty matters, it may ask the human rather than silently inventing an interpretation.

Research:

* camera hardware,
* camera protocols,
* Raspberry Pi versus dedicated camera devices,
* RTSP/WebRTC/etc.,
* local video processing,
* scene-change detection,
* lightweight CV models,
* multimodal LLMs,
* inference hardware,
* retention strategies,
* bandwidth implications,
* night vision / low-light considerations,
* device security,
* network segmentation.

### B. Telegram communication

Telegram is a candidate initial communication channel because it offers a relatively simple way for the AI and human to communicate remotely.

Research whether it is actually the best first option.

Evaluate:

* Telegram bot APIs,
* security properties,
* privacy limitations,
* polling vs webhook architecture,
* attachments,
* voice,
* images,
* commands,
* proactive messages,
* authentication,
* alternatives.

Do not assume Telegram must remain the permanent UI.

The communication abstraction should support future clients.

# 8. Progressive capability and trust model

One important design principle should be:

> Capabilities are progressively granted rather than universally assumed.

Different users may choose different levels.

For example:

* chat only,
* chat + memory,
* health data,
* computer telemetry,
* camera,
* microphone,
* speaker,
* cloud APIs,
* autonomous software deployment,
* external communication,
* financial actions.

The system should maintain explicit knowledge of what it can and cannot do.

Permissions should be observable and auditable.

However, avoid producing a system where every action causes an annoying approval dialog.

Distinguish carefully between:

* capability permission,
* policy,
* goal,
* approval,
* autonomy,
* risk level.

Develop a coherent model for these concepts.

# 9. Autonomy philosophy

Default philosophy:

> The human defines or agrees upon the goal and governing policies. Within those boundaries, the AI may autonomously act.

The AI should not require approval for every action.

Users should be capable of defining prohibited or approval-required classes of actions.

Example policies:

```text
NEVER:
- attack, exploit, compromise, or disrupt third-party systems
- intentionally violate another person's privacy
- attempt to bypass the system's own safety controls

REQUIRE APPROVAL:
- send messages to another human
- spend more than £X
- delete irreplaceable data
- expose a new service publicly
- create or modify cloud IAM
- rotate critical credentials

AUTONOMOUS:
- analyze personal observations
- update internal memory
- run experiments inside sandbox environments
- modify low-risk dashboards
- create pull requests
- deploy reversible internal tools
```

These are examples, not final policy.

Design a much stronger policy system.

Investigate ideas such as:

* policy-as-code,
* capability tokens,
* risk scoring,
* sandboxing,
* taint tracking,
* approval workflows,
* least privilege,
* scoped credentials,
* budget limits,
* rate limits,
* egress control.

# 12. The kill switch

A critical requirement is an **external control plane that the autonomous agent cannot disable or rewrite**.

Research how this should work.

Possible characteristics:

* physically or logically separate control plane,
* independent credentials,
* network-level cut-off,
* ability to revoke agent credentials,
* ability to disable cloud resources,
* ability to stop workloads,
* owner-only authentication,
* emergency read-only mode,
* recovery mode.

The agent should not possess the privileges required to remove its own ultimate shutdown mechanism.

Draw this explicitly in architecture diagrams.

Examples:

Consider:

* event sourcing,
* relational databases,
* object storage,
* semantic indexes,
* temporal databases,
* knowledge graphs,
* embeddings,
* summarization,
* archival tiers.

Answer questions such as:

* What becomes permanent?
* What expires?
* What gets summarized?

* How do we distinguish observation from inference?

# 19. Intervention evaluation

A central requirement:

> The system must measure whether its actions actually help.

Otherwise it becomes an elaborate notification generator.

Design how interventions are evaluated.

Examples:

```text
Hypothesis:
Morning reminder will increase probability of running.

Intervention:
Send reminder at 07:30.

Observation:
Run occurred / didn't occur.

Evaluation:
Estimate intervention usefulness.

Decision:
Keep / modify / remove.
```

Explore:

* experiments,
* A/B or N-of-1 testing,
* causal inference where realistic,
* observational metrics,
* user feedback,
* counterfactual uncertainty,
* intervention fatigue.

This feedback loop may be one of the most important differentiators of the system.

# 35. Avoid framework lock-in

Assume today's fashionable agent libraries may disappear.

Architect around stable primitives.

Prefer:

* APIs,
* processes,
* queues,
* schemas,
* durable storage,
* versioned protocols,

# 37. AI-generated architecture changes

Therefore distinguish:

### Runtime learning

Changing:

* memory,
* preferences,
* thresholds,
* schedules.

### Configuration evolution

Changing:

* policies,
* model routes,
* plugin configuration.

### Software evolution

Changing:

* application code.

### Infrastructure evolution

Changing:

* services,
* databases,
* networks,
* cloud resources.

### Governance evolution

Changing:

The agent should not casually rewrite its own governance layer.

# 57. Simplicity is a requirement

At every stage ask:

> What is the simplest system that preserves the important long-term boundary?

Do not deploy enterprise infrastructure merely because the future system could become large.

A system for one person should not accidentally become Google-scale architecture cosplay.

But equally:

Do not take shortcuts that create irreversible architectural debt.

Make that distinction explicit.

---

# 58. Privacy stance

Do not optimize for users unwilling to provide useful data.

This project may intentionally require meaningful permissions in order to provide meaningful value.

It is acceptable to say:

> “This capability requires access to X. If you are uncomfortable with X, disable the capability, but its associated experience will not work.”

Avoid pretending that a zero-permission experience can provide equivalent functionality.

At the same time:

* make permissions transparent,
* minimize unnecessary collection,
* give users clear data ownership,
* expose retention,
* provide deletion,
* isolate credentials,
* protect against accidental external transmission.

Be opinionated rather than misleading.

Versioned contracts.

Documentation as infrastructure.
Design for years.
Build only what is needed now.
