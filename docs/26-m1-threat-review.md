# M1 implementation threat review

## Status

This is an implementation threat review for the current M1 preview as of
2026-08-18. It is not a production security signoff. The reviewed
implementation is a strong owner-facing preview, but M1 remains incomplete for
production because audit coverage, cross-store audit atomicity, backup/export
scope, restore execution, observability, and clean acceptance evidence are not
closed.

The review uses the security objectives in
[09-security-threat-injection.md](09-security-threat-injection.md), the ranked
risks in [20-risk-register.md](20-risk-register.md), the current M1 inventory in
[25-m1-implementation.md](25-m1-implementation.md), and the Guardian contract in
[contracts/guardian-protocol.md](contracts/guardian-protocol.md).

## Findings

| ID | Priority | Finding | Required action |
| --- | --- | --- | --- |
| TR-001 | P0 for production | Event/audit coverage is broad but not universal, and most source mutations still append audit evidence through separate service/store calls rather than one source-plus-audit transaction. PostgreSQL owner sessions are the exception: session issue/revoke audit is coupled inside the same database transaction. | Keep M1 status as preview. Expand audit category by category, state source/audit failure semantics per path, and only claim atomicity where one transaction actually covers both records. |
| TR-002 | P0 for production | Export is correctly limited to portability. PostgreSQL is now the separate recovery authority: the synthetic drill restores every migrated table and directly traverses nonempty conversation, model/evidence, memory, session, and audit state through an encrypted logical snapshot and clean owner API. It still does not prove an installation schedule, offsite copy, key custody, blob coverage, or backup expiry. | Keep export and recovery separate. Before a personal-data deployment, configure and test owner-controlled local/offsite restic destinations, recovery-key custody, pruning/expiry, backup-age alerts, and any external blob scope. |
| TR-003 | P1 | The Codex CLI route is bounded and explicit, but it is not production host isolation. It launches a local process as the current OS user with read-only/no-approval/ephemeral flags and a stripped environment. | Keep it disabled unless explicitly configured and labelled as an approved-provider disclosure route. Require stronger OS/container isolation before treating it as production-safe. |
| TR-004 | P1 | Telegram text/pairing/delivery boundaries are strong for preview, but production media/blob handling and some transport deduplication are intentionally incomplete. Bot API successful-send dedupe is process-local, and ambiguous send outcomes become permanent failures to avoid duplicate sends. | Add durable send de-duplication and a production attachment/blob backend before claiming complete Telegram production support. Keep ambiguous-send retry disabled unless an external idempotency proof exists. |
| TR-005 | P1 for production | The preview proxy now accepts only an exact HTTP(S) origin using `localhost`, loopback, RFC1918, or IPv6 ULA. It rejects credentials, paths, queries, fragments, public/link-local/carrier-shared/DNS targets, ambiguous or embedded address forms, and raw controls before listening. This prevents the prior arbitrary-origin header-forwarding path, but literal validation does not authenticate the core or create network isolation. | Preserve the same-origin/private-literal boundary. Before a production deployment, pin the exact core target in reviewed deployment policy and add trusted TLS/service identity plus host/network controls; do not treat address classification alone as authorization. |
| TR-006 | P1 | Current clean acceptance evidence still depends on Director reconciliation of generated files and Docker-dependent PostgreSQL/recovery proof. | Finish generated evidence refresh and prove integration/recovery in a clean environment with the pinned PostgreSQL image available. |

## Production Blockers

1. Complete event/audit coverage for every important mutation, authorization,
   denial, egress, and owner-visible state transition.
2. Define and implement source-plus-audit atomicity where needed. Where stores
   remain separate, document the failure mode and detection path.
3. Configure the implemented logical SQL/restic recovery path for a real host:
   local and offsite destinations, independent key custody, expiry/pruning,
   backup-age monitoring, external blob scope, and periodic clean-host drills.
4. Bind the production web proxy to an exact reviewed core target with trusted
   service identity/TLS and host/network policy; the preview's private-literal
   validation is necessary but not a production trust channel.
5. Treat Codex CLI routing as experimental until it has stronger process and
   filesystem isolation.
6. Add production Telegram durability for send deduplication and attachment blob
   handling before broad Telegram claims.
7. Refresh generated evidence and rerun clean CI-equivalent, integration, and
   recovery checks after current Director/Forge changes settle.

## Overall Judgment

No evidence found in this review shows ambient model/tool authority, Guardian
mutation authority in Melloa, unauthenticated owner mutations, direct model
credential leakage in normal route code, or a false claim inside the export
manifest. The primary risk is overclaiming: strong preview controls can look
production-ready unless the remaining audit, recovery, isolation, and evidence
gaps stay explicit.
